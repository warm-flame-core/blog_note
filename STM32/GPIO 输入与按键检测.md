# 引言

上一篇写到最后，`GPIO` 给我的感觉是能指挥了：让哪个引脚高就高，让哪个低就低，一路追到 `BSRR` 寄存器上。但那是我单方面在说话。板子始终在自说自话，它不知道我什么时候按了按键。

我按下按键，它总得知道。可按键接到引脚上之后，我读到的究竟是个什么东西？按下算 `1` 还是算 `0`，凭什么是这样？

`GPIO` 的八种模式里，输入占了四种。概念篇把它们的电路一层层拆过，那是纸上推演；真要拿一个按键接到板子上，挑哪一种、为什么挑这种，我还没想过。

---

## 一、 板子上的四个按键

### 1.1 原理图上的接线

板子上有四个按键，原理图给它们所在的那几条连线起的名字是 `SYS_SW1` 到 `SYS_SW4`，板子上印的也是这几个字。它们挂在同一个端口 `GPIOG` 上，接法完全一样。原理图里长这样：

![[STM32/attachments/STM32开发板按键接线.png|四个按键与上拉电阻、并联电容的接线]]

单看 `SYS_SW1` 这一路：

- `VDD_3.3V` 经过一个 `10 kΩ` 的电阻（`R43`）接到 `SYS_SW1` 这条网络上；
- 按键 `SW6` 一端接 `SYS_SW1`，另一端直接连到地；
- 一个 `100 nF` 的电容（`C51`）与按键并联。

`SYS_SW1` 是这条连线的网络标号：一头接按键 `SW6`，另一头通到芯片的 `PG10`。其余三路只是换了电阻编号和引脚。

那个 `10 kΩ` 电阻是整条电路的支点。按键断着的时候，`SYS_SW1` 这条网络跟地之间没有通路，电流只能从 `VDD_3.3V` 经过电阻流过来，引脚被顶在 `3.3V` 附近，是个确定的高电平。按键一按下去，网络直接接地，电阻两端的压差全落在它自己身上，引脚被拉到 `0V`。

如果没有这个电阻，按键断着的时候引脚是悬空的，电压是多少谁也说不准，读出来的值自然没有意义。这跟概念篇里讲过的那两个根本问题是一回事：输入要能被读出确定的值，那一端必须有人给出确定的电平。

### 1.2 按键状态与引脚电平

照着上面的接法，引脚状态跟按键动作的对应关系就定死了：

| 按键状态 | 开关 | 引脚电平 | `IDR` 里对应的位 | 代码里读到的值 |
| --- | --- | --- | --- | --- |
| 松开 | 断开 | `3.3V`（高） | `1` | `GPIO_PIN_SET` |
| 按下 | 闭合 | `0V`（低） | `0` | `GPIO_PIN_RESET` |

这张表里最别扭的是最后一行：按键按下去，代码读回来的是 `GPIO_PIN_RESET`。这个宏的名字里有“复位”，看着像在读某个错误状态，其实它就代表低电平。后面判断按键时反复要写 `== GPIO_PIN_RESET`，读成“这个引脚现在是低”就行。

这种“按下是低”的接法在板子上非常常见，但它不是天经地义的。同样一颗按键，另一端接 `VDD` 而不是接地，结论就整个反过来：松开是低、按下是高。判断条件反过来写着才对，照抄别人的经验值会翻车。

### 1.3 标号与引脚

四个按键在原理图上按 `SYS_SW1`、`SYS_SW2`、`SYS_SW3`、`SYS_SW4` 排序，但落到引脚上并不是顺着 `PG6`、`PG7`、`PG8`、`PG10` 排下来的：

| 板子上的标号 | 芯片引脚 | 封装上的引脚号 |
| --- | --- | --- |
| `SYS_SW1` | `PG10` | 125 |
| `SYS_SW2` | `PG6` | 91 |
| `SYS_SW3` | `PG8` | 93 |
| `SYS_SW4` | `PG7` | 92 |

这四个引脚不是顺着排下来的：`PG10`、`PG6`、`PG8`、`PG7`，第三个和第四个还是反的（`SYS_SW3` 走 `PG8`，`SYS_SW4` 反倒走 `PG7`）。要是想当然地按顺序往上套，`KEY3`、`KEY4` 就会写到错的引脚上，按下去灯不亮，还得回头查半天。

这张表在代码里要落成枚举与引脚的映射，是后面 BSP 那一节的底稿。

## 二、 按键抖动

### 2.1 理想波形与实际波形

如果按键是个理想的开关，波形应该是干净的方波：按下的一瞬间电压落到 `0V`，松开的一瞬间回到 `3.3V`，中间稳稳当当。

实际不是这样：

![[STM32/attachments/按键抖动波形.png|理想波形与实际的按下毛刺、释放毛刺]]

竖虚线标出的是理想状态的跳变时刻，实线画的是引脚上真实发生的电压。在按下和松开的那一瞬间，电压并不会一步到位，而是在新旧电平之间反复横跳好几下，书上把这种毛刺称作抖动。

`1.1` 节里那个 `100 nF` 电容，干的就是这件事。

### 2.2 抖动的持续时间

抖动的来源有两处：手指按下去时的晃动，以及金属触点自己弹了几下。两个原因叠在一起，引脚上就出现了那段来回跳的电平。

- 抖动时间一般在 `5 ms` 到 `20 ms` 之间，常见的是 `5 ms` 到 `10 ms`；
- 工程上按最坏情况设计，也就是按 `20 ms` 算。

这个数字直接决定后面消抖延时该取多少。取小了盖不住毛刺，取大了按键就变得迟钝，按下去要等一下子才有反应。

### 2.3 并联电容的作用

原理图里那个跟按键并联的电容，可以当成一块海绵：

- 按键松开时，电流只能从电阻慢慢流过来，电荷一点点攒到电容上。想让它两端的水位差涨起来需要时间，松开瞬间那几个毛刺就被抹平了；
- 按键按下时，电容里的电荷顺着按键流到地上，水位差只能慢慢降下来，按下瞬间的抖动同样被抹平。

两条路都在拖慢电压变化的速度，原本一蹦到顶的跳变被拉成一条斜坡，软件读到的就干净多了。

不过它管的只是电压变化有多快。触点在闭合、弹开时自己还会弹好几毫秒，跳变次数一多，光靠拖慢速度盖不住，这部分要交给代码。

### 2.4 施密特触发器管不到的地方

概念篇里讲过，引脚内部有 `TTL` 施密特触发器，它专治不规整的输入。那它跟抖动不是正好对口吗？

不是一回事。施密特触发器解决的是“信号不干净”的问题：输入电压停在两个阈值之间时，它靠迟滞区域把输出稳住，不让输出跟着噪声反复翻转。它管的是电压不够干脆的情形。

抖动属于“信号乱跳”：电压是实打实地在高、低之间来回穿越，幅度足够大，速度也不慢。它每一次都可能穿过迟滞区间，触发器当然就跟着一次次翻转。

![[STM32/attachments/施密特触发器迟滞区域.png|施密特触发器的迟滞区域]]

所以抖动这件事，芯片内部那个施密特触发器指不上：外面那个电容能压掉一部分，剩下的要代码来处理。

## 三、 输入模式的选择

### 3.1 四种接法

引脚要能被读出确定的值，高电平和低电平这两端都得有人负责。外部电路能扛起哪一端，缺的那一端交给芯片内部的上下拉去补，`GPIO` 的输入模式就是按这个道理定下来的。

按键无非就是“按下时把引脚接到哪儿”，只有两种可能：接地，或者接 `VDD`。剩下的一端谁来补，就有了四种搭配。

| 方式 | 按键按下时接到 | 谁给出高电平 | 谁给出低电平 | 引脚配置成 |
| --- | --- | --- | --- | --- |
| 方式1 | 地 | 芯片内部上拉 | 外部按键 | 上拉输入 |
| 方式2 | `VDD` | 外部按键 | 芯片内部下拉 | 下拉输入 |
| 方式3 | 地 | 外部上拉电阻 | 外部按键 | 浮空输入 |
| 方式4 | `VDD` | 外部按键 | 外部下拉电阻 | 浮空输入 |

**外部电路缺哪一半，就由内部补哪一半；外部两半都齐了，内部就什么都不用管。**

### 3.2 方式1与方式2

方式1 是最省元件的一种：按键一端接地，另一端直接进引脚，外面什么电阻都不加。

按键松开时，这条线上没有任何外部来源，得靠芯片内部的上拉把引脚顶到高电平；按下时开关接地，又把引脚拽到低电平。所以引脚要配成**上拉输入**。

![[STM32/attachments/按键输入方式1内部上拉.png|方式1：外部只接地，内部上拉提供高电平]]

图里画的是引脚内部那套结构：靠 `VDD` 那一侧的开关是内部上拉，靠 `VSS` 那一侧的开关是内部下拉。方式1 里下拉那个是断开的（红叉），只有上拉参与工作。

**方式2 跟它是镜像关系**：按键改成接到 `VDD`，外部就只能给出高电平，低电平这一半交给内部下拉，引脚配成**下拉输入**。两者的思路完全一样，只是上下颠倒一下。

### 3.3 方式3与方式4

板子上用的是第三种：外面自己带一个上拉电阻。

按键按下接地、松开靠外部电阻拉高，高低两端外部都包了，芯片内部的上拉和下拉就都用不上，两个开关全断开，引脚配成**浮空输入**。

![[STM32/attachments/按键输入方式3外部上拉.png|方式3：外部上拉电阻提供高电平，内部上下拉都断开]]

**方式4 是它的镜像**：外部换成下拉电阻，同样配浮空输入。

这里容易绕进去的一点是：既然是“上拉”，为什么不干脆配成上拉输入？因为内部的上拉开关一闭合，就等于在外部那颗 `10 kΩ` 电阻旁边又并了一颗电阻上去。并联之后等效阻值变小，静态电流变大，而且两个电阻谁说了算也没个准数。外部已经把这段路铺好了，内部就别再插手。

> [!note] 内部上下拉的定位
> 芯片内部的上下拉算“缺省能力”：不用加元件，一根线接上去就能有个大致的电平。但它的阻值固定、偏弱，也没法按需求调整。
>
> 外部电阻的阻值可以自己定，灵活性大得多，还能根据后面接的器件去配。所以很多硬件工程师宁愿在外面多放四颗电阻，也不动内部那套。

### 3.4 配置里跟按键有关的几项

`CubeMX`（`STM32CubeMX`，意法官方的图形化配置工具）里配一个输入引脚，跟按键有关的就这么几项：

| 配置项 | 取值 | 说明 |
| --- | --- | --- |
| `GPIO mode` | `Input mode` | 引脚方向设成输入 |
| `GPIO Pull-up/Pull-down` | `No pull-up and no pull-down` | 外部已有上拉，内部两个都关掉，即浮空 |
| `User Label` | `SYS_SW1` 之类 | 用户标签，给引脚起个看得懂的名字 |

`User Label` 只是个给自己看的记号。引脚一多，`PG10` 这种编号对不上号，标成 `SYS_SW1` 之后回头看配置一眼就明白它是干什么的。

配置完生成的初始化代码跟输出引脚是同一套模板，只是填进去的参数不同：

```c
/*Configure GPIO pins : PG6 PG7 PG8 PG10 */
GPIO_InitStruct.Pin = GPIO_PIN_6|GPIO_PIN_7|GPIO_PIN_8|GPIO_PIN_10;
GPIO_InitStruct.Mode = GPIO_MODE_INPUT;
GPIO_InitStruct.Pull = GPIO_NOPULL;
HAL_GPIO_Init(GPIOG, &GPIO_InitStruct);
```

上一篇已经把这四行拆到寄存器层面看过一遍，这里只提一点：`GPIO_MODE_INPUT` 和 `GPIO_NOPULL` 这两项合起来，落到 `CRL`/`CRH` 里就是输入模式的编码，内部的上下拉开关不会被接通。

## 四、 读一个引脚的完整过程

### 4.1 读取接口

读引脚只有一个函数：

```c
GPIO_PinState HAL_GPIO_ReadPin(GPIO_TypeDef *GPIOx, uint16_t GPIO_Pin);
```

参数说明：

- `GPIOx`：目标端口，取值 `GPIOA` 到 `GPIOG`
- `GPIO_Pin`：要读的引脚位图，多个引脚可以用 `|` 组合

返回值：`GPIO_PIN_SET`（高电平）或 `GPIO_PIN_RESET`（低电平）

注意事项：引脚得先配成输入模式，配置没做或者做错了，读回来的值没有意义

### 4.2 函数实现

函数体一共十来行，真正干活的就一句：

```c
GPIO_PinState HAL_GPIO_ReadPin(GPIO_TypeDef *GPIOx, uint16_t GPIO_Pin)
{
  GPIO_PinState bitstatus;

  /* Check the parameters */
  assert_param(IS_GPIO_PIN(GPIO_Pin));

  if ((GPIOx->IDR & GPIO_Pin) != (uint32_t)GPIO_PIN_RESET)
  {
    bitstatus = GPIO_PIN_SET;
  }
  else
  {
    bitstatus = GPIO_PIN_RESET;
  }
  return bitstatus;
}
```


- `assert_param(IS_GPIO_PIN(GPIO_Pin))` 是参数合法性检查，确认传进来的位图是库认识的取值。这个宏在没开断言的时候会被整个抹掉，不参与运行；
- 关键的一句是 `(GPIOx->IDR & GPIO_Pin) != (uint32_t)GPIO_PIN_RESET`。它把 `IDR` 寄存器整个读进来，然后跟传进来的引脚位图做按位与；
- 结果不等于 `0`，说明那个位上是 `1`，函数返回 `GPIO_PIN_SET`；否则返回 `GPIO_PIN_RESET`。

所以读引脚这件事，拆到底就是**读一次 `IDR` 寄存器，再做一次按位与**。

### 4.3 IDR 寄存器

`IDR` 的正式名字叫端口输入数据寄存器，参考手册里的定义是这样：

![[STM32/attachments/STM32_GPIOx_IDR寄存器.png|参考手册里 GPIOx_IDR 的位定义]]

- 地址偏移 `0x08`，排在前面的两个配置寄存器 `CRL`（偏移 `0x00`）、`CRH`（偏移 `0x04`）之后，输出数据寄存器 `ODR`（偏移 `0x0C`）之前；
- 位 `15:0` 一共 16 位，第 `y` 位对应引脚 `Py`，读出来就是那个引脚此刻的电平；
- 位 `31:16` 保留，始终读为 `0`；
- 这个寄存器是只读的，手册里特别注明“只能以字（16 位）的形式读出”。

### 4.4 按位与的作用

`GPIO_PIN_10` 这个宏展开出来是 `0x0400`，也就是二进制里第 `10` 位为 `1`、其余全为 `0` 的一个数。既然要看的是第 `10` 位，那就拿它当掩码，把别的位一律抹掉：

```text
IDR            ???? ?1?? ???? ????      16 个引脚的电平，只有第 10 位是我关心的
GPIO_PIN_10    0000 0100 0000 0000      1 << 10，也就是 0x0400
--------------------------------------------------
IDR & 掩码      0000 0?00 0000 0000      与完之后只剩第 10 位
```

按位与的规则是“全 `1` 才得 `1`”：掩码上是 `0` 的位置，不管 `IDR` 原来是多少，结果都是 `0`；掩码上是 `1` 的位置，结果原样保留。所以与完之后，如果这个数不是 `0`，唯一的原因就是第 `10` 位（也就是 `PG10`）此刻是高电平。

这也解释了为什么一个 `uint16_t` 类型的位图能一次带上好几个引脚：`GPIO_PIN_8|GPIO_PIN_9` 就是把两个位都置 `1`，与完的结果非 `0` 就表示“这几个引脚里至少有一个是高”。多个按键同时判断时这个性质很有用，但想分辨具体是哪一个，还得一位一位地测。

上一篇讲 `BSRR` 时说过，写引脚是把位图写进对应的寄存器。读和写用的是同一套位图，`GPIO_PIN_x` 既能当写的目标，也能当读的掩码，这是 `GPIO` 这套接口里比较省事的一处设计。

### 4.5 IDR 与 ODR 的区别

写引脚时落进的是 `BSRR` / `ODR`，读引脚时读的是 `IDR`。两个寄存器长得像，位置也挨着，但装的不是一回事：

- `ODR` 里存的是**我让它输出什么**；
- `IDR` 里存的是**引脚上实际是什么**。

正常推挽输出时两者看着是一致的，所以容易混起来。但碰到开漏输出就分家了：开漏输出的高电平不是芯片推出来的，而是靠外部上拉电阻把线拉上去的。`ODR` 里写的是 `1`，`IDR` 读到的也确实是高，可这个高跟芯片内部的输出级没什么关系。

反过来说，如果想知道一个引脚此刻真实的状态，就该去读 `IDR`，别去看自己写了什么。

## 五、 按键检测的三个版本

### 5.1 按键状态的直接映射

最小的一步：读一次按键，按结果写一次灯。

板上的灯是低电平点亮的，所以下面几段里 `GPIO_PIN_RESET` 是亮、`GPIO_PIN_SET` 是灭，跟 `1.2` 里按键的逻辑正好反着来。

```c
while (1)
{
  if (HAL_GPIO_ReadPin(GPIOG, GPIO_PIN_10) == GPIO_PIN_RESET)
  {
    HAL_GPIO_WritePin(GPIOF, GPIO_PIN_8, GPIO_PIN_RESET);
  }
  else
  {
    HAL_GPIO_WritePin(GPIOF, GPIO_PIN_8, GPIO_PIN_SET);
  }
}
```

按住按键灯亮，松手灯灭，接口就这么跑通了。

这一版其实也不是完全没问题。按下去的那一瞬间，引脚上的电平不是一步落到低，中间可能回冲到高，灯就跟着闪了一下。只是它马上就稳定成低电平，眼睛基本看不出来，所以出问题的概率低，也不好复现。

### 5.2 状态翻转与抖动放大

想要“按一下亮、再按一下灭”，光看当前电平不够了，得把灯的状态记住：

```c
bool led_status = false; // false: 灭，true: 亮

while (1)
{
  if (HAL_GPIO_ReadPin(GPIOG, GPIO_PIN_10) == GPIO_PIN_RESET)
  {
    led_status = !led_status;
    HAL_GPIO_WritePin(GPIOF, GPIO_PIN_8, led_status ? GPIO_PIN_RESET : GPIO_PIN_SET);
  }
}
```

逻辑上是每读到一次低电平就翻转一次，看着没问题。实际烧进去按几下就会发现结果说不准：有时候按一下亮了，有时候按一下没反应，有时候自己在那里闪。

问题就出在 `2.2` 节那段抖动上。主循环跑一圈花不了多少时间，`72 MHz` 的主频下，那十几毫秒的抖动里循环能跑上万圈。每一圈只要读到低电平就翻转一次灯，抖动期间电平来回跳了多少次，灯就跟着翻转了多少次。最后停在亮还是灭，取决于这段抖动里电平跳了奇数次还是偶数次，纯粹看运气。

这也说明一件事：抖动不是“偶尔读错一次”，在快的循环里它会被放大成一串翻转。这一版正好把抖动从“看不出来的小毛病”变成了“必然出问题”。

### 5.3 枚举与 BSP 层的解耦

一个按键一个灯还好办，四个按键四个灯之后，主循环里全是 `GPIOG`、`GPIO_PIN_10` 这样的字眼，读起来费劲，改起来也容易错位。

工程上的做法是在应用层和硬件之间隔一层，应用层只说“按键几”、“灯几”，不碰引脚号。做法是先给按键和灯各定义一个枚举：

```c
typedef enum
{
  LED1 = 1,
  LED2,
  LED3,
  LED4
} LED_t;

typedef enum
{
  KEY1 = 1,
  KEY2,
  KEY3,
  KEY4
} KEY_t;
```

再写一层函数把枚举翻译成具体的引脚。这层通常叫 `BSP`（`Board Support Package`，板级支持包），意思是“只负责板子上这些东西怎么用”的代码：

```c
// 按键被按下返回 true，否则返回 false
bool BSP_KEY_IsPressed(KEY_t key)
{
  bool ret = false;
  switch (key)
  {
  case KEY1: // PG10
    ret = (HAL_GPIO_ReadPin(GPIOG, GPIO_PIN_10) == GPIO_PIN_RESET);
    break;
  case KEY2: // PG6
    ret = (HAL_GPIO_ReadPin(GPIOG, GPIO_PIN_6) == GPIO_PIN_RESET);
    break;
  case KEY3: // PG8
    ret = (HAL_GPIO_ReadPin(GPIOG, GPIO_PIN_8) == GPIO_PIN_RESET);
    break;
  case KEY4: // PG7
    ret = (HAL_GPIO_ReadPin(GPIOG, GPIO_PIN_7) == GPIO_PIN_RESET);
    break;
  default:
    break;
  }
  return ret;
}
```

映射关系全部收在这个 `switch` 里，`1.3` 节那张表就是它的内容。往后再动硬件，改这一处就够了，主循环一行都不用碰。

主循环这边先回到最简单的“按住就亮”，把结构搭清楚，抖动的问题下一版再处理：

```c
BSP_KEY_IsPressed(KEY1) ? BSP_LED_On(LED1) : BSP_LED_Off(LED1);
BSP_KEY_IsPressed(KEY2) ? BSP_LED_On(LED2) : BSP_LED_Off(LED2);
BSP_KEY_IsPressed(KEY3) ? BSP_LED_On(LED3) : BSP_LED_Off(LED3);
BSP_KEY_IsPressed(KEY4) ? BSP_LED_On(LED4) : BSP_LED_Off(LED4);
```

灯那一侧也是同样一层封装，`BSP_LED_On(LED1)`、`BSP_LED_Off(LED1)` 往里同样是先查枚举对应的引脚，再调 `HAL_GPIO_WritePin`。

我在这里踩过一个坑：当时顺手写成了 `BSP_KEY_IsPressed(KEY1) ? BSP_LED_On(KEY1) : BSP_LED_Off(KEY1)`，拿按键的枚举去索引灯。两组枚举值恰好都是 `1` 到 `4`，编译不报错，烧进去跑起来也是对的，因为 `KEY1` 和 `LED1` 的值都是 `1`。

这种错误编译器拦不住，只能靠命名去防。`KEY_t` 和 `LED_t` 是两个不相干的类型，语义上不能混着用，可它们底层的数值就是这么巧。真要防死，得用更强的类型手段，或者干脆在每个枚举里把取值错开（比如灯的枚举从 `0x10` 起）。现在这样写，靠的是自己看清楚。

### 5.4 延时二次确认

抖动躲不掉，那就在代码里绕开它：**读一次不算数，等一会再读一次，两次都是低才认。**

```c
#define KEY_DEBOUNCE_MS 20

bool BSP_KEY_IsPressed(KEY_t key)
{
  bool ret = false;
  switch (key)
  {
  case KEY1:
  {
    if (HAL_GPIO_ReadPin(GPIOG, GPIO_PIN_10) == GPIO_PIN_RESET)
    {
      // 延时消抖后二次确认，过滤机械抖动的毛刺
      HAL_Delay(KEY_DEBOUNCE_MS);
      if (HAL_GPIO_ReadPin(GPIOG, GPIO_PIN_10) == GPIO_PIN_RESET)
      {
        ret = true;
      }
    }
  }
  break;
  // 其余三个按键同理
  default:
    break;
  }
  return ret;
}
```

第一次读到低电平只能说明“此刻是低”，可能是真的按下去了，也可能正好撞在毛刺上。等 `20 ms` 再看一眼：如果还在低，那就不是毛刺了，因为抖动的持续时间远小于 `20 ms`，这一下已经把整段抖动跨过去了。

`20 ms` 这个数字不是随便定的，它来自 `2.2` 节说的抖动时间上界。取小了跨不过去，取大了按键会变得迟钝。

另外一头也得管。上面这段只管了“按下”，如果程序需要在松开时做点动作，同样得等松开稳定之后再确认一次。做法是：确认按下之后翻转一次状态，然后卡在 `while` 里等引脚变高（等用户松手），松开之后再补一次延时。

> [!warning] 阻塞式消抖的代价
> `HAL_Delay` 是死等，这 `20 ms` 里 `CPU` 什么也干不了。四个按键轮着判断，每个都可能等一次 `20 ms`，主循环就被拖慢了。
>
> 另一种做法是不在主循环里等：让定时器定期去看一眼引脚，或者用中断记下按下的时刻，主循环只负责读结果。定时器与中断还没学到，上面这一版先用着。

## 六、 接口清单与容易踩的地方

### 6.1 本篇用到的接口

| 接口 | 作用 | 备注 |
| --- | --- | --- |
| `HAL_GPIO_ReadPin(GPIOx, GPIO_Pin)` | 读一个引脚的电平 | 返回 `GPIO_PinState`，实质是读 `IDR` 再做一次按位与 |
| `GPIO_PIN_SET` / `GPIO_PIN_RESET` | 读回来的两种结果 | `SET` 是高电平，`RESET` 是低电平 |
| `GPIO_PIN_x` | 引脚位图 | 读的时候当掩码用，多个引脚可以按位或组合 |
| `HAL_Delay(ms)` | 毫秒级延时 | 消抖用，会阻塞 |
| `GPIO_MODE_INPUT` / `GPIO_NOPULL` | 输入模式与上下拉 | 配置阶段填进 `GPIO_InitTypeDef` |

### 6.2 几个记住的点

- **按键按下读到的是 `GPIO_PIN_RESET`**。名字叫“复位”，但它就是低电平的意思，别被字面绕进去。
- **“按下是高还是低”由外部接法决定**。同一颗按键接 `VDD` 还是接地，判断条件是反的，不要照抄别人的写法。
- **`IDR` 才是引脚的真实状态**。想知道引脚上到底是什么电平就去读它，不要看自己往输出寄存器里写了什么。
- **外部电路决定了引脚该配哪种输入模式**。缺哪一半就由内部补哪一半；外部两半都齐了，就配浮空，内部上下拉都关掉。
- **抖动是按键的固有属性**，芯片内部的施密特触发器解决不了，并联电容能压一部分，剩下的交给软件。
- **消抖的延时必须盖住抖动时间**，取 `20 ms` 这个上界是最省心的做法。
- **消抖要管两头**，按下和松开都要确认，只做一半的话另一头照样会出问题。
